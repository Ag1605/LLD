Adapter Design Pattern – Complete Theory (LLD)
1. What is Adapter Design Pattern?
The Adapter Design Pattern is a Structural Design Pattern that allows two incompatible interfaces to work together.

In simple language:

Adapter acts as a bridge between two classes that cannot communicate directly because their interfaces are different.

It converts the interface of an existing class into an interface that another class expects.

Real-world example: Mobile Charger
Imagine:

Your mobile requires a USB-C charger.

You have an old charger with a Micro-USB connector.

Both connectors are different.

You cannot connect them directly.

What do you do?

You use an adapter that converts Micro-USB into USB-C.

2. Why do we need Adapter Pattern?
Imagine you are developing a payment application.

Your application expects every payment service to have this function:
makePayment();


But you want to integrate an existing third-party payment library.

The third-party library provides:
payAmount();


Now there is a problem:
- Your application expects makePayment().
- The third-party library provides payAmount().
- Both perform the same operation, but their interfaces are different.
You cannot directly use the third-party class through your expected interface.

Solution: Create an Adapter that converts makePayment() into a call to payAmount().



Problems without Adapter
1. Incompatible Interfaces: Two classes have different method names or structures.
2. Code Modification: You may need to modify existing or third-party code.
3. Tight Coupling: Client code becomes dependent on specific implementations.
4. Integration Difficulties: Integrating legacy systems and external libraries becomes difficult.
Adapter Pattern solves these problems without requiring changes to the existing class.

3. Main Components of Adapter Pattern
There are four important components.
1. Client
The class or application that wants to use a service.

It communicates through the interface it expects.

Example: Payment Application.
2. Target Interface
Defines the interface that the client expects.

Example:
class Payment {
public:
    virtual void makePayment() = 0;
};


The client expects makePayment().
3. Adaptee
The existing class that has an incompatible interface.

Example:
class OldPaymentSystem {
public:
    void payAmount() {
        cout << "Payment Done";
    }
};


It provides payAmount() instead of makePayment().
4. Adapter
The Adapter connects the Target Interface and Adaptee.

It implements the Target Interface and internally calls the Adaptee's method.

In our example:
- Client calls makePayment().
- Adapter receives the request.
- Adapter calls payAmount() on the old system.

4. How Adapter Pattern Works
Client

Requests makePayment()

Adapter

Converts the request

Adaptee

Executes payAmount()


Execution steps:
1. Client requests an operation using the Target Interface.
2. Adapter receives the request.
3. Adapter converts the request into the format expected by Adaptee.
4. Adapter calls the Adaptee method.
5. Adaptee performs the operation.
6. Result is returned to the client if required.

5. Types of Adapter Pattern
There are two commonly discussed implementation approaches.
A. Class Adapter
- Uses inheritance to connect the Target and Adaptee.
- Adapter inherits from the Target Interface and Adaptee.
- Often implemented using multiple inheritance in C++.
- Can be less flexible because it depends on inheritance.

B. Object Adapter
- Uses composition instead of inheriting from Adaptee.
- Adapter contains an object of the Adaptee class.
- Adapter delegates requests to that object.
- More flexible because the Adaptee can be replaced or injected.

6. Difference Between Class Adapter and Object Adapter
Feature	Class Adapter	Object Adapter
Approach	Inheritance	Composition
Adaptee	Inherited	Stored as an object
Flexibility	Less flexible	More flexible
Multiple inheritance	Often required in C++	Not required
Reusability	More limited	Generally better
Preferred	Less common	More common


7. Advantages of Adapter Pattern
1. Reusability: Allows existing classes to work with new systems.
2. Loose Coupling: Client depends on the Target Interface rather than the Adaptee.
3. Legacy Integration: Helps integrate old systems with modern applications.
4. Code Modification Avoidance: Existing third-party classes usually do not need modification.
5. Flexibility: Different implementations can be connected through adapters.
6. Separation of Concerns: Interface conversion logic stays inside the Adapter.
8. Disadvantages of Adapter Pattern
1. Additional Classes: Requires creating extra Adapter classes.
2. Increased Complexity: Adds another layer between Client and Adaptee.
3. Performance Overhead: Additional method calls and conversions may introduce small overhead.
4. Maintenance: Too many adapters can make an application difficult to manage.
5. Not Always Necessary: If two interfaces are already compatible, an Adapter is unnecessary.

10. Adapter vs Decorator vs Facade
These three patterns are often confused in interviews.
Pattern	Main Purpose
Adapter	Converts one interface into another
Decorator	Adds additional functionality to an existing object
Facade	Provides a simplified interface to a complex subsystem

Remember:
- Adapter = Makes incompatible interfaces compatible.
- Decorator = Adds new behavior.
- Facade = Simplifies access to complex functionality.
11. Adapter vs Bridge Pattern
Both patterns involve abstractions and implementations, but their purposes are different.
Adapter	Bridge
Makes existing incompatible interfaces work together	Separates abstraction from implementation
Usually applied during integration	Usually designed into the system architecture
Focuses on compatibility	Focuses on independent variation
Example: Legacy payment integration	Example: Different remote controls and devices


12. SOLID Principles and Adapter Pattern
Adapter Pattern is associated with several SOLID principles.

1. Single Responsibility Principle (SRP)

The Adapter has one main responsibility: converting one interface into another.

2. Open/Closed Principle (OCP)

We can introduce new adapters for new third-party services without changing the existing client code, provided the Target Interface remains unchanged.

3. Dependency Inversion Principle (DIP)

The client depends on the Target abstraction rather than directly depending on the concrete Adaptee.

13. When Should You Use Adapter Pattern?
Use Adapter Pattern when:
- Two classes have incompatible interfaces.
- You want to integrate a third-party library.
- You want to reuse legacy code.
- You cannot modify an existing class.
- You want different services to work through one common interface.
- You need to convert data or method calls between different systems.
Avoid it when:
- Interfaces are already compatible.
- A simple direct method call is sufficient.
- Adapter layers introduce unnecessary complexity.
